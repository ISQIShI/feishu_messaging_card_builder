# 正式设计前的开放问题

这些问题用于约束未来方案选择，不是当前阶段的实施任务清单。

## Hermes 边界

- 未来工具应作为 Hermes 内部扩展、外部代理、平台 adapter 包装层，还是独立服务？
- 哪些 Hermes 消息应转换为卡片：最终回复、过程消息、工具调用摘要、审批消息，还是全部飞书输出？
- 卡片交互回流 Hermes 时，应复用 Hermes 的 `/card ...` 命令事件，还是定义额外协议？
- 如果必须修改 Hermes 源码或运行环境，最小可逆边界是什么？安装、检查、更新、卸载和恢复分别应记录哪些状态？
- websocket 模式下，最小侵入接入出站消息的稳定边界在哪里？

## 飞书卡片生命周期

- 项目标准的发送路径应使用哪个官方端点和 payload 形态来发送 `card_id`？
- 每条 Hermes 输出是否都创建新卡片实体，还是同一会话复用某张卡片？
- 卡片更新是整卡替换、组件级更新，还是只更新固定内容块？
- `card_id`、飞书 message ID、Hermes session/message ID 之间的映射由谁持久化？
- 何时认为卡片不可再更新，需要创建新卡片？

## 内容模型

- Hermes 输出中哪些结构必须被保留：标题、段落、代码块、表格、工具调用、附件、思考摘要、运行指标？
- 长回复应该拆为多张卡片，还是创建单张卡片并通过组件折叠、分页或更新呈现？
- 飞书 200 组件限制触发时应如何降级？
- Markdown 与 Card JSON v2 组件之间是否需要中间表示？

## 状态与可靠性

- 卡片创建成功但发送失败时如何处理？
- 发送成功但状态记录失败时如何恢复？
- 更新失败时应重试、发送新卡片、回退文本，还是提示用户？
- 多个 Hermes 事件同时更新同一张卡片时如何排序和去重？

## 安全与权限

- 飞书应用需要哪些权限才能创建、发送、更新卡片实体和处理卡片动作？
- 凭证由 Hermes 管理、本项目管理，还是由部署环境注入？
- 卡片内容中是否可能包含敏感工具输出，需要过滤或权限隔离？

## 兼容性

- 目标飞书客户端是否满足 Card JSON v2 的最低版本要求？
- 是否需要支持 Lark 国际版与飞书国内版的差异？
- Hermes 版本升级后，项目如何识别 adapter、事件结构或 session 结构变化？
- 如果 Hermes websocket 连接行为变化，本项目如何检测兼容性并安全降级？

## 项目形态

- 未来技术栈应优先贴近 Hermes 的 Python 生态，还是独立选择更适合服务化部署的栈？
- 仓库应产出库、服务、Hermes 插件、部署脚本，还是组合形态？
- 文档、测试和示例应围绕“实体生命周期”还是“卡片渲染效果”组织？
