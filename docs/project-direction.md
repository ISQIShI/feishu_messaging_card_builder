# 项目方向说明

## 目标

本项目未来要实现一个面向 Hermes 与飞书之间的消息卡片转换工具。它应把 Hermes 产生并准备发送到飞书的消息，转换成适合飞书展示和更新的卡片形态。

与旧实现不同，未来方案不应从“给 Hermes 打补丁并把最终文本改成 JSON 卡片”这一思路出发，而应重新审视 Hermes 的官方消息模型、飞书的官方卡片实体生命周期，以及两者之间需要补齐的桥接状态。

## 已确认方向

飞书卡片应使用卡片实体机制：先创建卡片实体，获得 `card_id`，再基于该 ID 发送与更新卡片。这个方向比直接发送一次性的卡片 JSON 更符合“可复用、可更新、可流式更新”的目标。

Hermes 与飞书之间的连接范围只考虑 websocket 模式。webhook 只作为官方能力背景保留，不进入项目设计主路径。

如果未来方案需要修改 Hermes 源码、Hermes 配置、运行目录、系统服务或任何非本项目文件，该修改必须具备可逆机制：安装时能记录原始状态，更新时能基于明确基线演进，卸载时能恢复到安装前或用户确认的安全状态。

## 目标能力

未来工具应优先服务这些能力：

- 将 Hermes 面向飞书的回复转换为飞书卡片实体；
- 保留 Hermes 对话、用户、群聊和命令处理的语义；
- 记录 Hermes 消息、飞书消息、卡片实体和更新状态之间的映射关系；
- 支持卡片创建后的更新，而不仅是一次性发送；
- 在卡片路径失败时，提供明确、可观测、可恢复的降级策略；
- 避免让卡片展示层反向污染 Hermes 的模型调用链和工具调用链。

## 非目标

这些内容不应成为第一阶段方向文档的默认目标：

- 复刻旧补丁包结构；
- 默认修改 Hermes `gateway/run.py`；
- 直接沿用旧的 Python 包、脚本、测试或配置格式；
- 把飞书卡片当作普通 Markdown 渲染器；
- 把一次性 JSON 卡片发送当作主要路径；
- 把 webhook 连接方式作为首期设计范围；
- 引入不可追踪、不可卸载、不可更新的 Hermes 或外部环境修改；
- 在没有确认官方边界前承诺实时流式更新、富媒体内嵌或任意组件更新。

## 边界判断

Hermes 官方文档显示，Feishu/Lark 是 Hermes 支持的平台，Hermes 能处理飞书消息、群聊提及、附件、卡片按钮点击和命令事件。但 Hermes 文档没有给出通用的“创建飞书卡片实体并维护 card_id 生命周期”的抽象。因此，未来项目需要承担一层桥接职责：在 Hermes 语义和飞书卡片实体之间建立稳定映射。

飞书官方文档则显示，可更新卡片应围绕卡片实体和 `card_id` 运作。也就是说，未来项目的核心复杂度不只是“把文本变漂亮”，而是“把 Hermes 的消息与会话语义投射到飞书卡片实体生命周期”。

## 设计原则

### 1. 以实体生命周期而非输出格式为中心

卡片 JSON 是卡片实体的内容描述，不应成为项目的唯一核心模型。核心模型应回答：这张卡片从哪条 Hermes 消息来、对应哪个飞书会话、创建了哪个 `card_id`、是否已发送、还能否更新、失败后如何恢复。

### 2. 让 Hermes 保持语义来源地

Hermes 仍应是对话、工具调用、用户上下文和命令处理的来源。卡片工具应尽量避免改变模型调用链，只在消息交付和展示层接管必要责任。

### 3. 让飞书卡片保持状态来源地

飞书卡片实体的 `card_id`、组件 ID、更新窗口和客户端兼容性应被视为独立约束。不能假设 Hermes 的消息 ID 天然等价于飞书卡片 ID。

### 4. 优先可观测与可回退

卡片创建、发送、更新和降级都应能被记录。卡片失败不应让 Hermes 对话不可用；但降级方式必须避免重复发送、错乱更新或丢失用户上下文。

### 5. 分离内容理解、卡片建模和投递状态

文本结构化、Card JSON v2 建模、卡片实体 API 调用、发送和更新状态记录应是不同关注点。这样未来技术选型可以变化，而项目边界不被旧实现锁死。

### 6. 只围绕 websocket 主路径设计

websocket 是当前唯一设计目标。所有连接、鉴权、事件接收、状态同步和部署假设都应围绕 websocket 模式展开；webhook 相关内容只用于理解 Hermes 官方能力，不应成为接口、配置或测试矩阵的一部分。

### 7. 外部改动必须可逆

任何离开本仓库边界的改动都必须有生命周期管理：安装、状态检查、更新、卸载和失败恢复。即便未来选择修改 Hermes，也不能依赖手工补丁或不可审计的覆盖写入。可逆性是项目边界的一部分，不是实现后的附加脚本。

## 方向性风险

- Hermes 文档没有明确给出通用卡片实体更新流程，桥接层需要自己定义持久状态。
- 只支持 websocket 可以显著收窄复杂度，但会排除只能部署 webhook 的环境。
- 飞书 Card JSON v2 有客户端版本、元素数量、`element_id`、`update_multi` 等约束，不能把任意 Hermes 输出无损映射为卡片。
- 如果未来需要改动 Hermes 或运行环境，可逆机制会增加交付成本，但能避免升级、回滚和故障恢复不可控。
- 如果目标是“同一张卡片持续更新”，就必须明确更新窗口、失败补偿、并发更新和组件 ID 稳定性。
- 如果目标仅是“最终回复更好看”，则卡片实体机制仍可使用，但状态系统可以更轻；这两种方向的复杂度不同。
