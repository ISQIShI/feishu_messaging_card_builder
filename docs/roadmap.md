# 发展方向与路线图

本文档定义项目长期方向。它不是短期任务排期，而是用于约束未来多个阶段的选择：哪些原则必须稳定，哪些技术细节可以延后，什么时候需要重新决策。

## 长期愿景

本项目应成为 Hermes 与飞书卡片实体之间的可靠桥接层：理解 Hermes 的消息与会话语义，生成符合 Card JSON v2 约束的卡片内容，创建飞书卡片实体，维护 `card_id` 生命周期，并支持后续发送、更新、降级和恢复。

长期目标不是“把回复渲染得更好看”这么简单，而是建立一条可维护的消息交付路径：Hermes 负责 agent 与对话语义，飞书卡片实体负责展示与更新，本项目负责两者之间的转换、状态和可逆集成。

## 稳定原则

这些原则不应随技术栈或实现方式轻易改变：

1. 连接范围以 websocket 为主路径，不为 webhook 设计首期架构。
2. 飞书卡片采用实体优先：创建卡片实体，维护 `card_id`，再发送和更新。
3. Hermes 或外部环境的任何修改都必须可逆、可检查、可更新、可卸载。
4. Hermes 的模型调用链、工具调用链和会话语义不应被卡片展示层污染。
5. 卡片内容模型、卡片实体状态、发送更新机制和安装管理应保持关注点分离。
6. 失败路径必须明确：不能因为卡片失败导致 Hermes 对话不可用或重复发送混乱。

## 可变选择

这些内容可以在后续阶段根据研究、原型和验证结果调整：

- 项目形态：库、服务、Hermes 扩展、adapter 包装层或组合形态。
- 技术栈：贴近 Hermes 的 Python 生态，或采用独立服务更合适的栈。
- 状态存储：本地文件、SQLite、外部数据库或由部署环境提供。
- 内容中间表示：是否引入独立 IR 来连接 Hermes 输出和 Card JSON v2。
- 更新粒度：整卡更新、批量更新、组件更新或混合策略。
- 降级策略：文本回退、新卡片补发、用户提示或人工恢复工具。

## 阶段路线

### Phase 0：方向冻结与资料基线

目标：形成当前文档集，明确 websocket-only、卡片实体优先、可逆外部改动、Git 规范和长期路线。

完成标准：

- 项目方向文档明确边界和非目标；
- Hermes 与飞书官方资料研究被记录；
- 开放问题可用于正式设计前评审；
- Git 规范和路线图成文。

### Phase 1：边界验证与最小原型

目标：验证不依赖旧实现的最小可行边界。重点不是做完整产品，而是确认 Hermes websocket 模式下可在哪里观察或接管出站飞书消息，以及飞书卡片实体创建、发送、更新链路是否可稳定跑通。

阶段产出应回答：

- Hermes 出站消息接入点在哪里最稳；
- 是否需要修改 Hermes，如果需要，最小可逆修改是什么；
- `card_id`、飞书 message ID、Hermes session/message ID 如何建立映射；
- 飞书卡片实体发送和更新的官方 payload 形态是否已确认。

### Phase 2：核心模型与可靠性基础

目标：建立项目核心领域模型，而不是直接堆渲染逻辑。

应稳定下来的概念包括：

- Hermes 消息输入模型；
- 卡片内容中间表示或等价抽象；
- Card JSON v2 生成边界；
- 卡片实体记录；
- 更新窗口、版本号、幂等键和失败状态；
- 安装、检查、更新、卸载和恢复机制。

### Phase 3：可用产品化路径

目标：形成可安装、可配置、可验证的第一版工具。它可以只覆盖有限场景，但必须端到端可靠。

优先场景：

- websocket 模式下的最终回复卡片化；
- 创建卡片实体并发送；
- 记录 `card_id` 与源消息关系；
- 基础整卡更新；
- 失败时可观测且可恢复；
- 可逆安装与卸载。

暂不强求：

- 全量过程消息卡片化；
- 任意组件级流式更新；
- 富媒体完全内嵌；
- 多平台通用抽象。

### Phase 4：增强更新与交互能力

目标：在核心路径稳定后扩展卡片交互与更新能力。

可能方向：

- 组件级更新和批量更新；
- 长回复分页、折叠或渐进式展示；
- 工具调用摘要和运行状态区域；
- 卡片按钮回流 Hermes 命令处理；
- 更细粒度的失败恢复和重试策略。

### Phase 5：长期维护与生态适配

目标：让项目能跟随 Hermes 与飞书官方能力变化长期维护。

重点包括：

- Hermes 版本兼容检测；
- 飞书 Card JSON v2 与 CardKit API 变化跟踪；
- 状态迁移机制；
- 发布、升级、回滚文档；
- 示例、诊断工具和维护手册。

## 决策检查点

每个阶段结束前，应明确回答这些问题：

- 当前选择是否仍满足 websocket-only 主路径？
- 是否产生了 Hermes 或外部环境修改？如果有，是否可逆？
- 是否仍以卡片实体和 `card_id` 生命周期为中心？
- 是否有隐含的一次性 JSON 发送路径变成主路径？
- 当前状态模型是否能解释失败、重试、更新和卸载？
- 当前文档是否足以让后来者理解为什么这样设计？

## 长期不变与可扩展性的平衡

项目需要稳定的是“边界和生命周期”，不是某个具体实现。只要仍满足 websocket-only、卡片实体优先、可逆外部改动、状态可恢复这些原则，具体技术栈、部署形态和更新粒度都可以根据验证结果调整。

这种路线能避免两个极端：一是过早把项目锁死为旧式补丁包；二是只保留抽象愿景而无法指导开发。每一阶段都必须交付能降低下一阶段不确定性的成果。
