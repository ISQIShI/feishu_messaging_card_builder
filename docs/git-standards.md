# Git 规范

本规范用于保持项目历史可读、可回滚、可审查。它从当前仓库最近提交风格出发，采用英文 Conventional Commit 风格，例如 `chore: restructure repo layout and migration docs`。

## 分支模型

长期分支：

- `main`：稳定基线，只接收已经验证过的变更。
- `dev`：集成分支，用于承载下一阶段准备进入稳定基线的工作。

工作分支从 `dev` 创建，命名格式为：

- `docs/<topic>`：文档、研究、治理规范。
- `feat/<topic>`：新增能力。
- `fix/<topic>`：缺陷修复。
- `refactor/<topic>`：结构调整或重构。
- `chore/<topic>`：仓库维护、工具链、依赖管理。

分支名使用英文小写和连字符，避免中文、空格和过长描述。

## 提交信息

提交信息使用英文 Conventional Commit：

```text
type(scope): short imperative summary
```

`scope` 可选。summary 使用小写开头的祈使句，不加句号。

常用类型：

- `docs`：文档变更。
- `feat`：新增用户可感知能力。
- `fix`：修复缺陷。
- `refactor`：不改变外部行为的结构调整。
- `test`：测试新增或调整。
- `chore`：仓库、依赖、脚本和维护性工作。
- `ci`：CI/CD 配置。
- `build`：构建系统或打包相关。

示例：

```text
docs: define websocket-only project roadmap
feat(card): create card entity record model
fix(feishu): preserve card update state on retry
refactor(hermes): isolate outbound message adapter
```

提交正文用于解释“为什么”，而不是重复“改了什么”。当变更涉及外部环境、Hermes 源码、迁移、回滚风险或安全影响时，正文必须说明风险和恢复方式。

## 原子提交

每个提交应表达一个可独立理解、可独立回滚的逻辑变更。

拆分原则：

- 文档、代码、测试、配置尽量按关注点拆分。
- 实现文件与直接对应测试应在同一个提交中。
- 大规模重命名、格式化和逻辑修改不要混在一个提交中。
- 删除旧实现与新增新实现不要混在一个提交中，除非不一起提交会导致仓库无法验证。

如果一个提交触及多个目录，提交正文应解释为什么它们必须一起变更。

## Pull Request 规范

每个 PR 应包含：

- 背景：为什么需要这个变更。
- 范围：明确包含什么、不包含什么。
- 验证：执行过哪些检查、测试或人工审阅。
- 风险：影响 Hermes、飞书、部署、状态存储或回滚的风险。
- 恢复：如果涉及外部环境或 Hermes 修改，说明卸载、更新、回滚路径。

PR 应优先小而完整。若一个 PR 同时修改架构、实现、测试和文档，应拆成多个依赖明确的 PR。

## 历史整理

本项目鼓励在合并前整理本地历史，但必须遵守安全边界：

- 不重写 `main` 或 `dev` 的共享历史。
- 已推送并被他人基于其工作的分支，不做强制改写，除非团队明确同意。
- 如需更新远端历史，使用 `--force-with-lease`，不用裸 `--force`。
- rebase 前确认工作区干净。

## 文档与代码同步

设计决策进入代码前，应先或同时更新相关文档。尤其是这些内容不能只存在于代码里：

- Hermes 接入边界；
- 飞书卡片实体生命周期；
- 状态存储模型；
- 安装、更新、卸载与恢复机制；
- 不兼容变更和迁移方式。

## 发布与标签

在正式实现前不定义版本发布策略。进入可运行阶段后，应采用语义化版本：

- `MAJOR`：不兼容的配置、状态、安装或 API 变化。
- `MINOR`：向后兼容的新能力。
- `PATCH`：缺陷修复、文档补充和兼容性修复。

任何影响 Hermes 源码或运行环境的版本，都必须提供升级与回滚说明。
